# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A curated, machine-readable index of open-weight LLMs. `models.yaml` is the **single source of truth**; the README table and everything else are generated from it. A set of Python scripts keep the index current by discovering new models on Hugging Face and staging them for human review.

## Commands

```bash
pip install -r requirements.txt

python -m pytest tests/ -v                    # full test suite (CI runs this)
python -m pytest tests/test_arena_resolve.py  # a single test file
python -m pytest tests/test_arena_resolve.py::test_name  # a single test

python scripts/validate.py        # schema-check models.yaml (CI gate; exits non-zero on any problem)
python scripts/render_readme.py   # regenerate README.md from models.yaml
python scripts/render_json.py     # regenerate models.json from models.yaml
python scripts/check_license.py --unverified   # licence evidence for rows still `?`
python scripts/pull_hf.py         # dry-run: auto-fill fields from HF (--write to apply)
python scripts/pull_aa.py         # scrape AA Intelligence Index -> aa_scores.yaml
python scripts/pull_aa.py --rejoin  # re-run the name->repo join offline, no fetch
python scripts/discover.py        # org sweep + arena merge -> candidates.yaml
python scripts/pull_arena.py      # scrape arena leaderboard -> arena_agent_rankings.yaml
```

Note: `pytest` is not on the base interpreter here — use the repo's `.venv` (`.venv/bin/python -m pytest ...`) or a venv where `requirements.txt` is installed.

Gated repos: every `meta-llama/*` and `google/gemma-*` repo serves `README.md` publicly but returns **401** for `config.json` and `tokenizer_config.json`, and the HF API's `config` expand carries no context field for them either — so without a token there is no readable source for their `context_window` and the rows park on `no-context-window`. `hf_meta.auth_headers()` sends a bearer token when `HF_TOKEN`, `HUGGING_FACE_HUB_TOKEN` or `HUGGINGFACE_TOKEN` is set, and both urllib fetchers use it. The token must belong to an account that has **accepted the Llama and Gemma terms** — a valid token that has not is still 401. It is entirely optional: with no token the header is omitted and those rows stay in the review queue. When a config fetch comes back 401/403 the row is flagged `gated_no_access` and reports `gated-repo-no-access` rather than the misleading `no-context-window` — the window exists, it is one access grant away. **A token alone is not enough:** the account must also be on each repo's authorized list, so a valid token whose owner has not accepted the terms still gets 403. The flag is re-derived every run and clears itself once access is granted.

Network caveat: `pull_hf.py`, `discover.py`, and `pull_arena.py` all reach out to `huggingface.co` / `arena.ai`, which some sandboxes block. They are designed to run on a normal machine or in CI. `pull_arena.py --no-resolve` parses without any HF calls; `pull_arena.py --html page.html` runs fully offline from a saved page.

## Two-file data model

- **`models.yaml`** — the reviewed, published index. Only this file is validated and rendered. Fields are documented in [SCHEMA.md](SCHEMA.md).
- **`candidates.yaml`** — a staging queue of *unreviewed* auto-discovered models, written by `discover.py`. Rows here carry extra discovery-only fields (`discovered_via`, `arena_rank`, `aa_index`, `downloads`, `needs_hf_repo`, `resolution_confidence`, `needs_review`). **These fields must be stripped when a row is promoted into `models.yaml`** — `validate.py` only checks `models.yaml`, so they would otherwise leak in. `discover.py` may **append** auto-promoted rows to `models.yaml`, but only ever appends — it never modifies, reorders or deletes an existing row, so anything already there stays exactly as a human left it. Every automated change lands as a PR; nothing commits to `main` directly. A row auto-promotes only if it clears the notability bar (AA index, arena rank, or ≥500k downloads), has no missing vitals, and passes the same per-row checks `validate.py` runs on every row in `models.yaml`; otherwise it waits in `candidates.yaml` with a `needs_review` list (vitals gaps and/or `schema-invalid: ...` validator complaints).

## Discovery pipeline (the core architecture)

The point of the pipeline is to surface frontier releases without a human hand-watching Hugging Face, while keeping a human as the final gate. Understanding it requires reading `discover.py`, `pull_arena.py`, and `hf_meta.py` together.

**`hf_meta.py`** is the shared construction path. Both discovery sources build candidate rows through `should_track()` (the filter) and `candidate_from_repo()` (the row factory), so a candidate has exactly one set of filter rules and one shape. `EXCLUDE_PATTERNS` drops quants/adapters/merges/non-generative heads; `ACCEPTED_LICENSES` and `COMMERCIAL_GUESS` are HF's license vocabulary (not clean SPDX), and every commercial-use value is a *guess* a reviewer must re-check.

**`discover.py`** does an **org sweep**, not a global scan. It issues one `list_models(author=org, pipeline_tag=…)` call per entry in `ORG_ALLOWLIST` **per tag in `SWEEP_PIPELINE_TAGS`**, deduped by repo id. This is deliberate: sorting all of HF by upload date returns finetunes and quantizations and essentially never a frontier release. **Adding an org to `ORG_ALLOWLIST` is how the tracker gains coverage.** A failure on one tag is logged and the other tags still run; only an org whose every tag query failed counts as `org_error` (`list_models()` is a generator, so each call is wrapped in `list(...)` inside the `try` to force the HTTP request where the `except` can catch it).

**The sweep asks for every modality it indexes.** `models.yaml` carries `text`, `vision-language` and `multimodal` rows, so `SWEEP_PIPELINE_TAGS` is `text-generation` plus `hf_meta.MULTIMODAL_PIPELINE_TAGS`; HF's `pipeline_tag` filter takes one value, so the union needs one request each. Asking only for `text-generation` made the sweep blind to 56 multimodal models, 11 of them notable — Qwen3.5-9B (13.4M downloads), Gemma 4 E4B, Qwen3.6-27B. `thinkingmachines` looked like a dead org for the same reason: six repos, none tagged `text-generation`, because Inkling is multimodal. Inkling reached the queue only because arena ranked it and `arena_candidates` fetches by repo id via `model_info`, which is tag-agnostic — an unranked multimodal flagship had nothing to find it. An allowlisted org returning nothing is re-queried once unfiltered so a dead org reads differently from one publishing only tags the sweep does not index.

**`pull_arena.py`** scrapes the arena.ai Agent Arena leaderboard and resolves each ranked model's display name to an HF repo. Key rule: **open-weight status is decided by whether a public weights repo actually resolves on HF** — never from the org name and never from arena's license label. Name→repo matching uses `score_match()` with `_MIN_PREFIX_RATIO` (a prefix must account for ≥70% of the longer slug, which rejects brand-prefix noise like `Grok 4.5` vs `grok`). `HF_AUTHOR_HINTS` scopes the HF search per org; an org mapped to `None` means "no HF namespace, never search". Inexact matches are flagged `needs_hf_repo: true` for a human to confirm. `KEYWORD_MAP` is only a search hint — it makes no open-weight claim.

**The merge.** `discover.py`'s `main()` calls `load_arena()` + `arena_candidates()` and merges arena-resolved repos into the org-sweep candidates, deduping on lowercased `hf_repo` and sorting so arena-ranked models lead the review queue (best rank first), unranked org-sweep finds following newest-first. **Arena is never load-bearing**: a missing, empty, or malformed `arena_agent_rankings.yaml` degrades gracefully to an org-sweep-only run rather than aborting it. `load_arena()` validates shape after parsing so valid-YAML-wrong-shape files can't crash it. (Nothing about `discover.py` as a whole is guaranteed to exit 0 — see "Promotion is schema-gated" below.)

**Widening coverage.** An allowlist only finds what it knows. `pull_arena.py` records leaderboard orgs it has no mapping for in the `new_orgs` key of `arena_agent_rankings.yaml`, and `discover.py` reprints them — the signal to add an org to `ORG_ALLOWLIST` (and its namespace to `HF_AUTHOR_HINTS`). `unmapped_orgs()` computes this over *every* parsed row, not just resolved ones, so it surfaces exactly the orgs lacking a mapping.

**Promotion is schema-gated.** `classify.route()` decides `promote` / `review` / `drop` for every candidate. `classify.missing_vitals()` only judges whether a *notable* row is worth promoting unassisted (MoE active params, context window, licence allowlist, `needs_hf_repo`, family-stem collision, derivative-or-base, and a promotion-signal gap — `signal-too-weak` when nothing reaches the bar, `signal-too-stale` when a qualifying arena rank or download count belongs to a release outside the recency window) — it says nothing about whether the row is even well-formed. `candidates.yaml` is hand-edited, so a carried-forward row can clear every vitals check while still being garbage (e.g. `release_date: "sometime in 2025"`); promoting that as-is would append it to `models.yaml` and then crash `render_readme.py`'s date sort with `TypeError`, and since the render step in `discover.yml` has no `continue-on-error`, that kills the whole weekly PR. `classify.schema_errors()` closes that gap by running `validate.row_errors()` — the exact per-row checks `validate.py` applies to `models.yaml` — on the candidate before `route()` will promote it; any failure demotes the row to `review` with `schema-invalid: ...` reasons instead. `validate.row_errors()` is the single source of these rules; nothing reimplements them. **`classify.review_reasons()` is what actually writes `needs_review`**, and it reports each gap once: a validator complaint about a field a vitals reason already named is suppressed (a missing context window produced both `no-context-window` and `schema-invalid: context_window must be a positive integer` — 28 of 32 entries in the real queue were echoes like that). The suppression keys on `validate.SchemaError.field`, not on message text, so rewording a validator message cannot silently bring the duplication back. `review_reasons` returns plain `str`, never `SchemaError` — the list goes straight into `yaml.safe_dump`, which raises on a `str` subclass. `row_errors` likewise reports an absent field once: the enum, allowlist and format checks are skipped for a field nobody set, since "is this value acceptable" has no meaning there.

**Carried rows freeze their HF-derived facts.** A staged row is never rebuilt — it is `known`, so no sweep touches it — which means every field it was born with is frozen. This has now bitten four fields: `arena_rank` (fixed by re-stamping each run), `gated_no_access` (built to avoid it), `modality`, and `params_total_b`. `discover.refresh_hf_facts()` re-derives the last two every run from **one** `model_info` response — fetching twice would double the request count on every carried row of every weekly run — and is **ungated by `missing_vitals`**: a row with no gaps is promotable, so a frozen wrong value on it is exactly the one that reaches `models.yaml`. Both halves overrule a hand-edited `candidates.yaml` value, the only edits there that do not carry forward; these are machine-derived facts and HF is the authority on them. Every change is printed.

`_refresh_modality` fixed three live rows (`thinkingmachines/Inkling`, `moonshotai/Kimi-K2.6`, `Kimi-K2.7-Code`) sitting as `text` while multimodal, staged before the pipeline requested `pipeline_tag`; `validate.py` waves `text` through as perfectly legal. It overwrites only on a definite differing answer — a `None` from `modality_of` means "we do not know", never "text".

`_refresh_params` is the worse case: `deepseek-ai/DeepSeek-V4-Flash` sat at `158.1` against a real `290.9`, a partial count frozen while the repo was still uploading shards, and `validate.py` checks only that the number is positive — a wrong total promotes silently and renders as fact beside measured figures. It also has to run **before** the re-enrichment loop, because `enrich_row`'s card tie-break resolves a family card by matching the row's own total against the variants the card names, and cannot do that against a total that disagrees with all of them. `params_active_b` is kept *consistent*, never recomputed: a dense row must satisfy validate's `active == total` rule, an MoE row whose active still equals its total is carrying the "activation unknown" sentinel and must keep carrying it, and a real MoE activation figure is left alone — it describes routing, not file size. **Neither half touches `models.yaml`**, which is append-only; a wrong value already promoted there stays until a human edits it.

**One review reason is a decision, not a gap.** Every `needs_review` reason except `family-already-tracked` is fixed by supplying a missing fact, so the next run promotes the row on its own. A family collision instead means the release collides with a family already in `models.yaml` and someone must choose supersede-or-coexist — and because `candidates.yaml` is rebuilt each run and `models.yaml` is append-only, a reviewer's answer had nowhere to live: the row regenerated identically forever. `family_collision_reviewed: true` on the candidate row is that answer (*coexist*). `classify.missing_vitals()` tests it with `is True`, never truthiness — `candidates.yaml` is hand-edited and `validate.py` never reads it, so a quoted `"no"` would otherwise be truthy and publish a row the reviewer explicitly rejected. It clears the collision reason only, and `discover.PROMOTION_STRIP_FIELDS` drops it on the way into `models.yaml`. *Supersede* stays a hand edit — `discover.py` only ever appends.

## README and models.json are fully generated — don't hand-edit them

`render_readme.py` rewrites the **entire** `README.md`, not just the region between the `MODELS_TABLE` markers. The surrounding prose is the `body` string inside `render_readme.py:main()`. Any hand-edit to `README.md` — table or prose — is silently reverted on the next render, and the `validate` workflow's `git diff --exit-code README.md` step then fails. **To change README prose, edit the `body` string in `render_readme.py`.**

`models.json` is the same index in the format people actually fetch, written by `render_json.py` with the arena rank and AA index joined in and in the same newest-first order as the table. It is regenerated and diff-checked by CI exactly like the README, so it can never drift from `models.yaml`. `render_json.FIELDS` is an allowlist, not a dict copy — the discovery-only fields must never be republished as part of the index — and `commercial_use_verified` is always emitted explicitly, because a consumer treating a missing key as "verified" turns the table's trailing `?` into a settled legal claim.

**Nothing in a generated file may read the clock.** `validate.yml` re-renders both files and fails on any diff, so a `date.today()` in rendered output turns CI red on the first day nobody runs discovery — and the badge would be claiming a freshness it does not have while doing it. The README's "last discovery run" badge therefore reads a `generated:` stamp that `discover.write_candidates()` writes into `candidates.yaml`; `render_readme.load_generated()` returns None on a missing or malformed file and the badge is simply omitted.

## CI

- **`validate.yml`** (every PR + push to main): runs `pytest`, then `validate.py`, then re-renders `README.md` **and `models.json`** and fails if either differs from the committed one.
- **`discover.yml`** (weekly, Mondays 13:00 UTC + manual dispatch): runs `pull_arena.py` and `pull_aa.py` (both `continue-on-error`, so neither source blocks discovery), then `discover.py --min-params 3`, then `validate.py` (so a schema-gate bug or a hand-edit gone wrong surfaces here as a readable validation error instead of as a `TypeError` deep inside the renderer), then unconditionally re-renders `README.md` and `models.json` (not just when a row was promoted — an AA-only score change with no new row still needs a fresh README or `validate.yml`'s diff check fails on the next PR), then opens a PR touching `models.yaml`, `candidates.yaml`, `arena_agent_rankings.yaml`, `aa_scores.yaml`, `README.md` and `models.json`. **The PR is still the human-in-the-loop gate**, but the gate has moved: `discover.py` itself now appends any row that clears the notability bar with no missing vitals and no schema errors (see "Promotion is schema-gated" above) straight into `models.yaml`, so review means (1) spot-checking auto-promoted rows — a trailing `?` on **Commercial** marks `commercial_use` as inferred from the licence tag, not read — and (2) working the `needs_review` queue still sitting in `candidates.yaml`, filling gaps by hand and letting the next run promote automatically.

## Two totals, because they are two quantities

`params_total_b` is **measured** — HF's summed safetensors count. `params_total_stated_b` is what the **vendor publishes**. They differ by a few percent because a checkpoint carries tensors a headline figure leaves out (DeepSeek-V3: 671 stated, 684.5 measured — the MTP module; GLM-5: 744 vs 753.9; Inkling: 975 vs 952.4, in that direction). Neither is wrong, and neither is a correction of the other.

This exists because the record was contradicting itself. `params_active_source` stores a verbatim card sentence, and a sentence like `"284B parameters (13B activated"` asserts a **total** as well as an activation figure — sitting beside a bare `params_total_b: 290.9` in 13 published rows. `enrich._record_stated_total()` now reports the quoted total through the `notes` out-parameter (the same seam `hf_meta.fetch_config` uses, chosen so the return shape stays a plain `(billions, quote)` pair for existing callers), and `discover.enrich_row` writes it to the row.

**Absence is the normal case and the figure is never invented** — 22 of 48 rows publish no distinct headline number, and for those the measured count *is* the published number. `validate.row_errors` rejects a stated value more than `STATED_TOTAL_TOLERANCE` (25%) from the measured one: they describe the same model, every real gap is under 4%, and a wider one means the figure was copied off another variant — exactly what `enrich._TOTAL_MATCH_TOLERANCE` (15%) guards at capture time, but a hand edit could otherwise reintroduce.

**The table prints the stated figure, falling back to measured** (`render_readme.display_total`). The vendor's number is what a reader arrives with; printing 684.5 for DeepSeek-V3 would make a correct table look wrong to more people than it informed. `models.json` carries both.

Before this split the column meant two different things depending on how a row got in: 13 hand-curated rows held vendor figures, 18 auto-promoted rows held tensor counts. The migration moved every curated value into `params_total_stated_b` and put the measured count in `params_total_b`, so the column now means one thing everywhere. **Rendered output for those rows did not change** — DeepSeek-V3 still prints 671.

## Verifying commercial_use

`commercial_use` on an auto-promoted row is inferred from the HF licence **tag** — uploader-supplied metadata nobody read — and `render_readme.commercial_badge` marks it with a trailing `?`. `scripts/check_license.py` gathers the evidence to clear that: what licence files the repo actually serves, whether the text matches a canonical licence (`LICENSE_MARKERS`, all markers required — a card *mentioning* Apache is not Apache), any restriction language in it, and the card's licence section. `.claude/skills/verify-commercial-use/` is the agent workflow over it.

**The failure it hunts is not a wrong tag** — it is a standard licence with use restrictions bolted on, which still tags `apache-2.0` and is not Apache-2.0. Hence `added_terms`. That scanner must skip `CANONICAL_BOILERPLATE`: Apache-2.0's own text says "you may not use this file except in compliance with the License" and (§5) "without any additional terms or conditions", and those two lines flagged **every clean Apache repo** on the first live run. Add a new false positive there **with a test**; never loosen `RESTRICTION_PATTERNS`, which costs real detections.

The skill puts the **agent in the reviewer's seat**: it researches the licence from the card's `license_link`, the vendor's own licence page or GitHub repo, and web search, then assigns `license` and `commercial_use` itself. The rule that keeps that honest is **knowledge directs the search but is never the evidence** — every determination cites a URL actually fetched and quotes the operative clause, and a run that cannot find the instrument leaves the marker rather than asserting from memory. Research is done **per vendor, not per row**: the first real queue of 18 rows was 7 decisions.

`link_contradicts_tag` catches a permissive tag whose own `license_link` points at a vendor-hosted licence page. It is a lead, not a verdict — the Gemma 4 link looked like a custom licence and turned out to serve unmodified Apache-2.0 (Google moved Gemma 4 off the Gemma Terms of Use that Gemma 1–3 used). The distinction that decides these cases is whether a prohibited-use policy is *incorporated into the grant* or merely linked from the same site; the second does not make a licence conditional.

`--apply` writes only the two outcomes needing no judgement — `confirmed` clears the `?`, `tag-only` sets `license_text_published: false` — and refuses `added-terms`, `tag-mismatch`, `unrecognised-text` and `fetch-failed`, which are a person's call. It never touches a row a human already verified, and replaces `license_notes` only while it is still the `AUTO-DISCOVERED` placeholder. `plan_edits` will not confirm a licence `COMMERCIAL_USE` has no entry for: identifying the text is not the same as knowing its consequence, and inventing one is the single thing this must never do.

**Three states, not two.** `?` was carrying two unrelated meanings, and 18 of the 26 unverified rows were the second: the vendor publishes no licence file at all. `†` now says that — a permanent fact about the release, not a backlog item. `apply_edits` does line surgery on `models.yaml` a row block at a time; an earlier version appended new fields when it saw the *next* row's `hf_repo` and silently attached them to the following model, so the block buffering is load-bearing and tested.

## Licensing

Two licences, split by what the thing is. Code (`scripts/`, `tests/`, workflows) is MIT — `LICENSE`. Data (`models.yaml`, `models.json`, `candidates.yaml`, `aa_scores.yaml`, `arena_agent_rankings.yaml`, the generated table) is CC-BY-4.0 — `LICENSE-DATA`, which carries the canonical Creative Commons legal code verbatim. `LICENSE` is kept as pure MIT text with no preamble so GitHub's licence detector reads it; the split is explained in the README's `## License` section (in `render_readme.py`'s `body`) and at the top of `LICENSE-DATA`. **Neither licence touches the model weights** — those stay under their vendors' terms, which is what the `license` column exists to record.

## Conventions that keep the data trustworthy

- **No benchmark field.** The anchor number is the Artificial Analysis Intelligence Index in `aa_scores.yaml`, written by `scripts/pull_aa.py` and joined on `hf_repo` (falling back to repo identity) at render time. AA covers recent models only, so `—` is expected and correct for older rows.
- **Set `commercial_use` by reading the actual license**, not the word "open". Values are `true` / `false` / `conditional`.
- **One row per model** — a family flagship or distinct sizes, never both.
- **MoE**: total params in `params_total_b`, routed/active in `params_active_b`; for dense models the two are equal (validated).
- New license strings must be added to the allowlist in `validate.py` in the same change.
- **`params_active_b` comes from the card, but a card is not one model.** `enrich.active_params_from_card()` reads the figure vendors publish, and the hard part is not the phrasing — it is that one card often describes a whole family. Two distinct activated figures on a page is the normal case (`DeepSeek-V4-Pro ... (49B activated) and DeepSeek-V4-Flash ... (13B activated)`, `gpt-oss-120b`/`gpt-oss-20b`, `GLM-5` quoting both its 355B and 744B variants), so the function abstains rather than attribute the wrong model's number. The tie-break is the row's OWN measured total: `_PAIRED_PATTERNS` capture a total and its activation figure in one breath, and a claim whose total lands within `_TOTAL_MATCH_TOLERANCE` (15%) of the row's is the one describing this model. Cards round to the headline figure while safetensors counts every tensor (`744B` vs `753.9B`), which is why the tolerance is percentage-based and loose. **Precision is tiered:** the vendor's A-notation (`26B-A4B`) is a *rounded* label and lives in `_ROUNDED_PATTERNS`, consulted only when no precise figure resolves — Gemma 4's card prints its own repo id beside a table cell reading `3.8B`, and treating those as rival claims published 4.0 for a 3.8B model. `active_params_from_repo_name()` is the same notation read off the repo id, a last resort for cards that state nothing (`Qwen3-VL-235B-A22B` states it nowhere else); it cross-checks the name's total against the row's and abstains on disagreement, so a distill or mirror cannot donate its figure. Measured over the 26 queue rows blocked on this field: **16 correct, 0 wrong, 10 abstained** — every abstention a card that genuinely states no figure.
- **The model card is not a source for `context_window`.** It is the right source for `params_active_b` (see the next bullet), but measured against 26 cards whose true window is known, a card-derived context window was **8 correct, 3 wrong, 15 no-answer** — and the failures are semantic, not fixable by better patterns. `gemma-4-26B-A4B` (really 262144) says "the small models feature a 128K context window, while the medium models support 256K"; `Qwen2-72B-Instruct` advertises "up to 131,072" and ships 32768; both NVIDIA Nemotron cards claim "up to 1M" against a real 262144. `validate.py` only checks the value is a positive int, so a wrong figure passes silently and renders as fact. Read the window from `config.json` (authenticated if gated) or leave it at 0 for a human.
